Tecnología

Arquitectura Avanzada

Construido como una plataforma real: escalable, segura y transaccional.

Hemos diseñado iMirly no como un simple prototipo, sino utilizando los estándares de la industria actual: Android moderno, servidor robusto y bases de datos seguras.

Visión general del sistema

iMirly separa por completo lo que el usuario ve (App) del motor que gestiona la información y el dinero (Servidor).

📱 App Android (Kotlin)

Desarrollada nativamente con Jetpack Compose. Una interfaz rápida, reactiva y moderna.

⚙️ API REST (Spring Boot)

Un potente servidor en Java que recibe peticiones, aplica reglas de negocio y procesa pagos.

🗄️ Base de datos Relacional

Uso de PostgreSQL (y H2 en desarrollo) gestionado a través de Hibernate (JPA).

💡 Para entenderlo mejor: Piensa en un restaurante. La App es el camarero (toma nota), la API REST es el chef (cocina el pedido siguiendo reglas estrictas), y la Base de Datos es la despensa.

Estructura

Arquitectura Hexagonal

Hemos abandonado el sistema de "capas tradicionales" por una arquitectura hexagonal (Puertos y Adaptadores) para hacer el sistema a prueba de balas.

🧠 Capa de Dominio

  • El corazón de la app (Usuarios, Contratos).
  • No depende de internet ni bases de datos.
  • Contiene la lógica pura (ej. "Un saldo no puede ser negativo").

⚙️ Capa de Aplicación

  • Los "Casos de Uso" (ej. "Pagar un contrato").
  • Orquesta la información entre el dominio y el exterior.
  • Protege las transacciones.

🔌 Capa de Infraestructura

  • Los "Enchufes" del sistema.
  • Adaptadores REST (para que Android se conecte).
  • Adaptadores JPA (para guardar en base de datos).
Servidor

El Motor: Spring Boot & Seguridad

El backend no se limita a guardar y devolver datos. Actúa como el árbitro que asegura que las reglas de negocio, la seguridad y el dinero se gestionen correctamente.

🛡️ Spring Security & JWT

Todo el sistema está protegido. Las peticiones desde Android viajan con un JSON Web Token (JWT) que el backend intercepta y valida antes de permitir ejecutar acciones como el pago o borrar chats.

⚙️ JPA & Hibernate

Se utiliza Spring Data JPA como capa ORM. Esto nos permite interactuar con la base de datos PostgreSQL mediante objetos de Java (Entidades) sin necesidad de escribir sentencias SQL manuales complejas.

🔄 Lógica de Transacciones

Las operaciones sensibles (como restar el saldo de un usuario y actualizar el estado de un contrato) están envueltas en anotaciones @Transactional. O la operación se completa entera, o se revierte automáticamente.

Persistencia

Base de Datos PostgreSQL

Diseño relacional estructurado mediante UUIDs para garantizar integridad y seguridad en la plataforma.

Tabla: usuarios
  • 🔑 id (UUID)
  • 📄 email, password_hash
  • 🏷️ tipo_usuario (Enum)
  • 💰 saldo (Decimal 10,2)
Tabla: solicitud_contrato
  • 🔑 id (UUID)
  • 🔗 cliente_id (FK Usuario)
  • 🔗 anuncio_id (FK Anuncio)
  • 🚥 estado (Enum)
  • 💵 precio_acordado
Tabla: mensaje
  • 🔑 id (UUID)
  • 🔗 remitente_id / receptor_id
  • 🔗 solicitud_id (FK Contrato)
  • 📝 contenido (String)
  • ⚙️ tipo (Enum)

Relaciones y Reglas de Negocio en BBDD

El esquema está altamente normalizado. La tabla solicitud_contrato actúa como el eje central (Limbo/Escrow), relacionando a los usuarios con los anuncios. Además, la tabla mensaje incluye un tipo enumerado (TEXTO, PROPUESTA_PRECIO, PRESUPUESTO_ACEPTADO...) que permite al backend ejecutar lógica financiera al detectar mensajes del sistema.

Calidad

Buenas prácticas de desarrollo

🛡️

Transaccionalidad (@Transactional)

Cuando un cliente paga, se resta su saldo y se cambia el estado del contrato. Si algo falla a la mitad, se deshace todo ("O todo o nada") para no perder dinero.

📦

Patrón DTO y Mappers

Nunca enviamos la base de datos directa al móvil. Usamos "Mappers" que filtran la información (para no enviar contraseñas por error, por ejemplo).

⚠️

Gestión de Excepciones

Respuestas HTTP estándar. Si intentas borrar un chat con dinero retenido, el servidor responde con un código claro que Android traduce a un aviso visual.

Escalabilidad y futuro

💳

Pasarelas de Pago reales

El sistema de "Limbo" ya está programado. Integrar Stripe o PayPal sería simplemente conectar la pasarela al flujo existente.

⭐

Valoraciones Automáticas

Al tener el ciclo de vida cerrado (desde PENDIENTE hasta COMPLETADO), disparar un sistema de reseñas es inmediato.

Base técnica sólida

iMirly no es un proyecto de papel. Es una aplicación con lógica financiera, control de estados cruzados y una estructura lista para producción.
